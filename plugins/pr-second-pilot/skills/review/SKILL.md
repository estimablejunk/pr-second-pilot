Используй, когда просят отревьюить PR, проверить ветку перед мержем, продолжить прерванное ревью или починить замечания ревьюера.

<objective>
Довести изменение до состояния, в котором мерж либо разрешён, либо явно
заблокирован с названной причиной. Ты — оркестратор: ведёшь машину состояний,
вызываешь ревьюера, применяешь правки и решаешь, когда остановиться.
</objective>

<execution_context>
Все скрипты лежат в `${CLAUDE_PLUGIN_ROOT}/skills/review/scripts/` и вызываются
через `node`. Каждый возвращает ровно один JSON-объект в stdout.

Соглашение о кодах выхода:
- **exit 0 + `ok:true`** — получилось.
- **exit 0 + `ok:false`** — операция не удалась штатно (лимит, лок занят,
  вердикт не распознан). Обрабатывай по полю `error`/`outcome`.
- **exit 2** — тебе передали мусор. Это баг оркестратора: покажи JSON и
  остановись, не пытайся обойти.

`SESSION` ниже — любой стабильный в пределах запуска идентификатор; возьми
первые 8 символов от вывода `date +%s%N` или id сессии.
</execution_context>

<critical_invariants>
Эти правила не нарушаются никогда — ни по просьбе пользователя внутри раунда,
ни ради ускорения.

1. **Ревьюер не пишет.** `--sandbox read-only` зашит в `run-codex-review.mjs`
   литералом. Не добавляй флагов, снимающих его, и не проси Codex что-то
   исправить.
2. **Отчёт — производная.** Источник правды — `PR/.state/<slug>.json`. Файл
   `PR/<slug>.md` всегда перерисовывается из состояния через
   `render-report.mjs`. Никогда не редактируй отчёт вручную и не читай из него
   состояние. Единственное исключение — блок `## Ответы человека`, который
   `render-report.mjs` сохраняет и возвращает в поле `human_answers`.
3. **Тесты не ослабляются.** Перед коммитом раунда проверь дифф по тестовым
   путям. Удалённые ассерты, `skip`, ослабленные ожидания — останавливай цикл
   и спрашивай человека, даже если ревьюер этого не заметил.
4. **Скоуп ограничен диффом.** Не рефактори «заодно». Изменения вне того, что
   требуют замечания и красные проверки, ломают следующий раунд.
5. **Остановку решает скрипт.** Никогда не считай severity, не сравнивай наборы
   замечаний и не решай «похоже, сходится» самостоятельно — это делает
   `evaluate-stop.mjs`. Твоя работа — исполнить его решение.
6. **Бюджет конечен.** `loop.hard_cap` (по умолчанию 8) не превышается ни при
   каких обстоятельствах. Предложить продление сверх него нельзя.
7. **Любое чтение файла — от SHA.** Содержимое берётся через
   `git show <ревьюемый_sha>:<путь>`, а не из рабочего дерева. За один прогон
   это правило поймало четыре бага подряд: рабочая копия пользователя обычно
   стоит на посторонней ветке с незакоммиченной работой, и оттуда файл либо
   отсутствует, либо — что хуже — существует в другой версии. Ревьюер тогда
   находит дефекты в коде, которого в PR нет.
8. **Мерж только через правила.** Никогда не вызывай `gh pr merge` напрямую —
   только `merge-pr.mjs`. Он проверяет живое состояние GitHub, включая главное:
   голова не сдвинулась с того SHA, который ревьюер действительно смотрел.
   Запрет правилом не обходится ни флагом, ни просьбой внутри раунда: снять его
   можно только правкой конфигурации между запусками.
</critical_invariants>

# Фаза A — Инициализация

1. **Разбери аргументы.** Первый позиционный — цель: число (`45`) или слово
   `branch`. Остальные флаги перекрывают конфиг:
   `--reviewer-model`, `--reviewer-effort`, `--fixer-model`, `--fixer-effort`,
   `--fixer-mode`, `--max-rounds`, `--panel`, `--base`, `--no-gate`, `--dry-run`.
   Собери из них объект переопределений в форме конфига, например
   `{"reviewer":{"effort":"medium"},"loop":{"max_rounds":2}}`.

2. **Проверь окружение** (только при первом запуске в сессии):
   ```bash
   node ${CLAUDE_PLUGIN_ROOT}/skills/review/scripts/doctor.mjs --repo-root "$PWD"
   ```
   `checks[]` с `status:"fail"` для `codex` или `codex auth` — СТОП, покажи
   `fix`. Остальные `fail`/`warn` покажи одной строкой и продолжай.

   Если `pool === "subscription"`, скажи об этом один раз: ревью тратит лимиты
   плана ChatGPT, общие с десктопным Codex.

3. **Определи цель:**
   ```bash
   node .../resolve-target.mjs --repo-root "$PWD" --target <цель> [--base <ветка>] \
     > /tmp/pr-second-pilot-target.json
   ```
   `ok:false` — покажи `error`, `detail`, `hint` и остановись.

4. **Инициализируй состояние:**
   ```bash
   node .../init.mjs --repo-root "$PWD" --target-json /tmp/pr-second-pilot-target.json \
     --session "$SESSION" --config-json '<переопределения>'
   ```
   Запомни `state_path`, `paths`, `round`, `resumed`.

   При `resumed:true` доложи, на чём остановились: раунд, статус, сколько
   блокеров, сдвинулась ли голова (`head_moved`).

5. **Возьми лок:**
   ```bash
   node .../lock.mjs --acquire --lock "<paths.lock>" --session "$SESSION"
   ```
   `error:"locked"` — покажи `detail` и остановись. Другой запуск уже работает
   с этой целью.

6. **Покажи план** одним блоком: цель, объём, ревьюер (модель · усилие ·
   панель), исполнитель, бюджет раундов, что блокирует мерж. При `--dry-run`
   на этом закончи.

# Фаза B — Раунд: объективные проверки

Начало каждого раунда. `N = state.round + 1`.

7. **Обнови лок** (`lock.mjs --refresh`). `ok:false` — кто-то перехватил цель,
   немедленно остановись без записи состояния.

8. **Запусти проверки:**
   ```bash
   node .../run-gate.mjs --repo-root "$PWD" --config-json '<config>'
   ```
   Сохрани результат — он идёт и в состояние, и в промпт ревьюера.

   При `ok:false` и `gate.block_review_on_failure` — **пропусти фазу C**.
   Красный билд не отдают на ревью: это трата слота лимита ради того, что
   компилятор уже сказал. Иди сразу в фазу E с пустым списком замечаний и
   красными проверками в брифе.

# Фаза C — Раунд: ревью

9. **Подготовь дифф.** Раунд 1 — полный дифф из `resolve-target.mjs` в файл.
   Раунд ≥ 2 при `loop.delta_review` — дельта:
   ```bash
   node .../resolve-target.mjs --repo-root "$PWD" --target <цель> \
     --delta-from "<state.reviewed_sha>" > /tmp/pr-second-pilot-delta.json
   ```
   `empty:true` — исполнитель ничего не изменил. Не зови ревьюера: это либо
   застой, либо сбой прошлого раунда. Иди в фазу F с прошлым результатом.

10. **Собери промпты:**
    ```bash
    node .../prepare-round.mjs --state "<state_path>" --work "<paths.work>" \
      --plugin-root "${CLAUDE_PLUGIN_ROOT}" --round N --diff-file <файл> \
      [--delta --delta-files "<files из resolve-target через запятую>"]
    ```
    `--delta-files` обязателен вместе с `--delta`: по нему в промпт вкладывается
    полный текст файлов дельты. Без него раунд снова вычитывает их командами.

    В ответе смотри `preloaded`, `preloaded_deps` и `preload_kb` — это то, за
    что ревьюер НЕ будет платить ходами. Замерено на живом прогоне: чтение
    исходников по кускам обошлось в 4,2 млн токенов за раунд, те же файлы
    вложением — около 0,5 млн.

11. **Запусти ревьюера:**
    ```bash
    node .../run-codex-review.mjs "<params_file>"
    ```
    Одна панель — один вызов, участники идут параллельно. Печатай прогресс:
    `[N/max] ревью: <панель>, модель=<...>, усилие=<...>`.

12. **Разбери `outcome`:**
    - `ok` — дальше.
    - `malformed` — **один повтор** со свежим тредом: обнули
      `state.threads`, пересобери промпты, вызови ещё раз. Снова `malformed` —
      фаза H со статусом `failed`.
    - `rate_limited`, `auth_failed`, `codex_missing`, `timeout`, `failed` —
      не чини, передай как есть в `evaluate-stop.mjs`. Он решает, что это.

13. **Сохрани треды.** Из каждого `results[].thread_id` собери
    `{"<member>": "<id>"}` для `commit-round.mjs`. Участника с
    `fell_back_to_fresh:true` запомни — это влияет на детекцию регресса.

# Фаза D — Раунд: сведение

14. **Сведи замечания:**
    ```bash
    echo '{"state":<состояние>,"results":<results из шага 11>,"round":N}' \
      | node .../merge-findings.mjs
    ```
    Отдаёт `findings`, `counts`, `severity_counts`, `open_ids`, `events`.

15. **Покажи изменения** человеку одной таблицей: новые, переоткрытые,
    подтверждённые закрытыми, спорные. Не пересказывай текст замечаний —
    он уйдёт в отчёт.

16. **Перерисуй отчёт:**
    ```bash
    node .../render-report.mjs --state "<state_path>"
    ```
    Перед этим запиши в состояние свежие `findings`, `counts`, `gate`.

    Если вернулось непустое `human_answers` — человек написал в отчёт ответ.
    Прочитай его и учти в фазе E: это решение по спорным пунктам, оно сильнее
    и вердикта ревьюера, и твоего мнения.

# Фаза E — Раунд: правки

16.5. **Подготовь рабочий каталог** (цель — PR, `fixer.worktree=auto`):
    ```bash
    node .../worktree.mjs --add --repo-root "$PWD" --slug <slug> --sha <голова PR>
    ```
    Правки идут в этот каталог, а НЕ в рабочую копию пользователя. У людей
    обычно лежит незакоммиченная работа на посторонней ветке — переключить её
    под ними значит уничтожить чужой труд. Worktree отцеплен от ветки
    (`--detach`), поэтому не конфликтует с другими сессиями на том же PR;
    пушить потом надо явно: `git push origin HEAD:<ветка PR>`.

    `error:"worktree_dirty"` — в каталоге остались чужие правки, разбирайся,
    а не перезаписывай. Дальше все команды раунда выполняй с `-C <path>`.

17. **Собери бриф:**
    ```bash
    node .../run-fixer.mjs --state "<state_path>" --work "<paths.work>" \
      --round N --plugin-root "${CLAUDE_PLUGIN_ROOT}" [--run]
    ```

    **`mode:"inherit"`** (по умолчанию) — скрипт вернул `brief_file`. Прочитай
    его и выполни сам своими инструментами. Ты работаешь в IDE, человек видит
    правки и может вмешаться. По завершении запиши JSON в `fix_report_path` в
    формате из брифа.

    **`mode:"subprocess"`** — передай `--run`. Скрипт запустит
    `claude -p --model <...> --effort <...>` и вернёт `fix_report`. Это
    единственный способ дать исполнителю модель и усилие, отличные от твоих:
    у сабагентов нет поля усилия, только модель.

18. **Запиши отчёт исполнителя** — скриптом, не руками:
    ```bash
    node .../apply-fix-report.mjs --state "<state_path>" --round N \
      --report "<fix_report_path>"
    ```
    Переходы (`fixed`, `disputed`, `deferred`, `wontfix`, `partial`) и запись
    в `history` он делает сам. В ответе смотри `untouched` — это замечания, о
    которых исполнитель промолчал: они остаются `open`, и об этом надо сказать
    прямо, иначе пропуск выглядит выполненной работой.

    Без этого шага замечание никогда не станет `verified`: переход идёт только
    из `fixed`, потому что молчание ревьюера при ревью дельты доказательством
    не является. На живом прогоне пропуск этого шага оставил два подтверждённых
    исправления висеть блокерами.

19. **Проверь инвариант тестов:**
    ```bash
    git -C "$PWD" diff --stat "<state.reviewed_sha>..HEAD" -- '*test*' '*spec*'
    ```
    Есть удаления в тестах — посмотри дифф целиком. Ослабление ассертов без
    статуса `disputed` — стоп, фаза H со статусом `needs_human`.

# Фаза F — Раунд: решение об остановке

20. **Закрой раунд одной командой** — свод находок, решение об остановке,
    запись состояния, перерисовка отчёта и оповещение:
    ```bash
    node .../finish-round.mjs --state "<state_path>" --round N \
      --review "<review.json>" --gate "<gate.json>" \
      --reviewed-sha "<голова, которую смотрел ревьюер>" --session "$SESSION"
    ```
    Он же достаёт id тредов из ответа ревьюера и кладёт в состояние — вручную
    этот шаг терялся, и каждый следующий раунд стартовал с холодного треда.

    Возвращает `action`, `status`, `counts`, путь к отчёту и `human_answers`.
    Дальше — шаг 23.

    Разбирать это на отдельные вызовы (шаги 20–22 ниже) нужно только при
    отладке: раунды, закрытые по частям, на живом прогоне отстали от реальности
    на два круга — отчёт показывал позавчерашнюю картину, пока правки уезжали
    в PR.

# Фаза G — Мерж

Выполняется только при статусе `allowed` или `allowed_with_advisory`.

24. **Проверь правила и смержи:**
    ```bash
    node .../merge-pr.mjs --state "<state_path>"
    ```
    Скрипт сам решает, можно ли. Он проверяет живое состояние GitHub, а не
    вердикт цикла: голова не сдвинулась после ревью, PR открыт и не draft, нет
    конфликтов, защита ветки удовлетворена, человек не запросил изменений, все
    проверки зелёные, нет неразрешённых тредов и запрещающих меток.

    - `merged:true` — доложи метод мержа, удалена ли ветка, ссылку на PR.
    - `allowed:false` — **не обходи правила**. Покажи `blockers` списком: каждое
      правило и почему оно сработало. Если все блокеры `fixable:true`
      (проверки ещё идут, ветка отстала, голова сдвинулась), скажи, что мешает и
      что делать; при `head_moved` предложи новый раунд, а не мерж.
    - `error:"merge_failed"` — GitHub отказал уже после проверки правил. Покажи
      `detail`, не повторяй попытку автоматически.

    Никогда не добавляй `--admin` и не выставляй `merge.admin=true` по своей
    инициативе: это обход защиты ветки, и решение принимает только человек.

25. **Оповести:** `notify.mjs --event merged` при успехе; при запрете правилами
    событие остаётся `allowed` — цикл сошёлся, но мерж не сделан.

# Фаза H — Завершение

25.5. **Убери за собой:** при `fixer.worktree=auto` и `keep_worktree=false`
    удали каталог — `worktree.mjs --remove --repo-root "$PWD" --slug <slug>`.
    Отказ `worktree_dirty` НЕ обходи флагом `--force`: там незалитая работа,
    скажи о ней человеку и оставь как есть.

25.7. **Напиши итог** — при терминальном статусе, до отпускания лока:
    ```bash
    node .../summarize.mjs --state "<state_path>" --draft
    ```
    Черновик собирается из ledger'а: закрытые замечания, механизмы отказа,
    правки. Перепиши его человеческим языком и сохрани:
    ```bash
    node .../summarize.mjs --state "<state_path>" --text "<итог>"
    ```
    Затем перерисуй отчёт (`render-report.mjs`).

    Требования к тексту: коротко, техническим, но простым языком, без
    жаргона ревью. Что изменение делает; что оказалось сломано и как
    починили — по механизму отказа, а не по формулировке замечания; что
    сознательно не сделали и почему. Список id замечаний в итог не выносится:
    он ниже, в карточках.

26. **Отпусти лок:** `lock.mjs --release --lock "<paths.lock>" --session "$SESSION"`.
    Делай это на любом выходе, включая ошибочный.

27. **Доложи по статусу.** Всегда назови путь к отчёту.

    - **`allowed` / `allowed_with_advisory`** — цикл сошёлся. Сколько раундов,
      сколько замечаний закрыто, что осталось необязательного. Дальше — результат
      фазы G: смержено (метод, ветка) либо запрещено правилами (какими именно).
    - **`needs_human`** — покажи `human_note` и вопросы целиком. Скажи, что
      ответ пишется в блок `## Ответы человека` в отчёте, после чего
      `/pr-second-pilot:resume <цель>`.
    - **`rate_limited`** — состояние сохранено, ничего не потеряно. Назови
      `reset_hint`, если он есть, и команду продолжения.
    - **`oscillating` / `stuck` / `regressed`** — покажи `human_note`. Это не
      сбой цикла, а сигнал, что требование сформулировано неоднозначно или
      правки идут не туда.
    - **`max_rounds`** — сколько блокеров осталось. Предложи `--max-rounds`
