# Профиль стека: Next.js App Router + TypeScript + Supabase

Подключается автоматически, когда в проекте найдены `next` и `@supabase/*`.
Конкретизирует общие категории — не заменяет их.

## Доступ к данным

**Политики на уровне строк (RLS) обязаны быть включены** для каждой таблицы с
пользовательскими данными. Фильтрация на клиенте контролем доступа не является.

Server Actions и Route Handlers обязаны получить пользователя из проверенной
сессии **до** любого запроса к данным. Идентификатор из тела запроса —
управляется атакующим.

```ts
// ❌ userId приходит из тела — подставляется атакующим
export async function POST(req: Request) {
  const { userId, data } = await req.json()
  await updateRecord(userId, data)
}

// ✅ личность берётся из проверенной сессии
export async function POST(req: Request) {
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return new Response("Unauthorized", { status: 401 })
  await updateRecord(user.id, data)
}
```

Ключ `service_role` — только в серверном коде. Никогда в переменной с префиксом
`NEXT_PUBLIC_`, никогда в клиентском бандле. На клиенте — только `anon`.

## Граница server/client

Секрет, прочитанный в серверном компоненте и переданный пропсом в клиентский,
уезжает в бандл. Передавай результат, а не секрет.

```tsx
// ❌ ключ окажется в клиентском бандле
export default function Page() {
  const apiKey = process.env.SECRET_API_KEY
  return <ClientComponent apiKey={apiKey} />
}

// ✅ секрет не покидает сервер
export default async function Page() {
  const data = await fetchWithSecret()
  return <ClientComponent data={data} />
}
```

Проверь и обратное: не помечен ли `"use client"` модуль, который тянет за собой
серверную логику или доступ к данным.

## Инъекции

Клиент Supabase параметризует запросы сам, но не везде:

```ts
// ❌ строковый фильтр с пользовательским вводом
await supabase.from("orders").filter(`status = '${input}'`)
// ❌ то же самое в rpc с интерполяцией
await supabase.rpc("search", { q: `%${input}%` })  // проверь тело функции

// ✅ параметризованные операторы
await supabase.from("orders").eq("status", input)
```

Функции БД с `SECURITY DEFINER` проверяй отдельно: у них должен быть явно задан
`search_path`, иначе вызывающий может подменить схему.

## XSS и переходы

- `dangerouslySetInnerHTML` — только с санитизированным содержимым.
- `href` в `next/link` с пользовательскими данными — проверь схему, разреши
  только `http`/`https` и относительные пути.
- `router.push(userControlled)` — либо список разрешённых, либо только
  относительные пути.

## Аутентификация

Магические ссылки и OAuth: `redirectTo` обязан проверяться по списку
разрешённых, а не браться из запроса. Токены сброса пароля — одноразовые и
короткоживущие; встроенные механизмы это соблюдают, самописные потоки часто нет.
Состояние OAuth и PKCE — на месте.

## Конфигурация

- Бакеты хранилища: публичные только там, где это осознанно.
- Заголовки безопасности в `next.config.ts`.
- Секреты подписи сессий заданы в проде.
- Route Handlers, написанные вручную, не наследуют встроенное ограничение
  частоты — на путях аутентификации его нужно добавлять.

## SSRF

Любой серверный `fetch(userUrl)` проверяется по списку разрешённых адресов. Чаще
всего это прокси картинок, тестировщики вебхуков, импорт по ссылке.

## Логи

Не логируй тела запросов целиком — там персональные данные и токены. Логируй
отказы аутентификации, отказы авторизации и неожиданные ошибки.

## Конвенции проекта

Если в репозитории есть `CLAUDE.md` или `AGENTS.md` с описанием слоёв (например
«запросы к БД только в `src/lib/supabase/queries/`», «серверное состояние через
React Query, глобальное состояние не используется», «формы через React Hook Form
и Zod») — эти правила сильнее общих рекомендаций. Нарушение объявленной проектом
архитектуры — находка уровня `minor`, а если через обход слоя утекает доступ к
данным — `major`.
